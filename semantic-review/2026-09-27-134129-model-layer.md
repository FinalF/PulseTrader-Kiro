# DayTrader model layer — five-file review

The most urgent issue is structural: `Portfolio.swift` does not exist, meaning the entire paper-trading layer (FR-05, US-15/16/17) has no aggregate type to build against and any ViewModel that touches portfolio state will not compile. Beyond that, there are financial math bugs in `Trade.unrealizedPnL` (direction-blind), `TradeSignal.riskReward` (degenerate input returns a valid-looking `0`), and `Stock.changePercent` (nil quote is indistinguishable from a flat stock). `ConfidenceTier` is missing `Codable`, API keys sit in source code, and `Quote.previousClose` defaults to `0` rather than `nil`, propagating silent bad state through change-percent calculations.

Watch for: **Portfolio.swift missing** (confirmed — compilation blocker for any paper-trading ViewModel), **API keys in source** (confirmed — violates NFR-05, will appear in version control), **`changePercent` returns `0.0` for unloaded stocks** (confirmed — `Stock.changePercent` conflates nil-quote with flat-on-the-day), **direction-blind `unrealizedPnL`** (confirmed — correct for longs only; breaks silently when `short` is added).

**Verdict**: NEEDS_CHANGES

---

## High-level view

`Quote.previousClose` defaults to `0`, so any bar constructed without an explicit prior close will cause `Stock.changePercent` to report 0% rather than "unknown." Since `changePercent` already returns `0.0` for a nil `latestQuote`, there are now two distinct "no data" states that are both silently zero — downstream sorts and filters cannot distinguish them.

`Stock.changePercent` returns `Double` instead of `Double?`, conflating "no quote yet" with "flat on the day." US-03 requires watchlist sorting by signal strength, which likely needs a secondary sort on change percent; unloaded stocks will sort as flat.

`Trade.unrealizedPnL` is direction-blind. The formula is correct for longs, but `TradeDirection` already has a `Codable` raw value on disk. Adding `short` without updating the formula produces wrong P&L on every short position with no compile-time warning.

`TradeSignal.riskReward` has a redundant guard and silently returns `0` when `stopLoss == entryPrice` — the same value `0` returns for a 0:1 risk/reward, masking a malformed signal as a merely bad one.

`Portfolio.swift` does not exist. `Configuration.paperTradingInitialCapital` provides the seed value, but there is no type to hold cash, positions, or the daily metrics FR-05.6 requires. This is the highest-priority gap.

API keys in `Configuration.swift` are static string literals. Any real key committed here violates NFR-05 and is effectively public once the repo is shared.

4. **`unrealizedPnL` is direction-blind** — `quantity × (currentPrice − entryPrice)` is correct for longs only. Add a direction multiplier (`direction == .long ? 1 : -1`) now, before `short` is added to `TradeDirection`, to prevent silent wrong-sign P&L.

### Missing Portfolio aggregate

`Portfolio.swift` does not exist in the module. `Configuration.paperTradingInitialCapital` anchors the starting state, and every FR-05 requirement assumes a type that holds cash, open positions, and the trade history needed to compute daily metrics. Without it, any ViewModel that wires to the paper-trading layer is a compilation error. US-15 (real-time unrealized P&L), US-16 (partial close), US-17 (equity curve), and FR-05.6 (win rate, profit factor) all depend on this type.

A minimal shape that satisfies v1:

```swift
struct Portfolio {
    var cash: Double
    var openPositions: [Trade]        // isOpen == true
    var closedTrades: [Trade]         // isOpen == false

    var equity: Double { /* cash + sum of unrealizedPnL across open positions */ }
    var dailyPnL: Double { /* sum of realizedPnL for today's closed trades */ }
    var winRate: Double { /* closedTrades where realizedPnL > 0, as a fraction */ }
    // profitFactor, averageWin, averageLoss, equityCurve per FR-05.6
}
```

Note that `equity` requires a current price per position — the Portfolio will need access to the live quote stream, either by passing current prices into a method or by holding a `[String: Double]` price map.

### API keys in source — NFR-05 violation

`Configuration.swift` defines `alphaVantageAPIKey` and `polygonAPIKey` as `static let` string literals. The current placeholder values are safe, but the architecture must change before US-18 (user-entered API key) lands: the key entry UI writes to Keychain via `SecItemAdd` / `SecItemUpdate`, and `Configuration` reads from Keychain. The current `static let` shape becomes a throwing function or a computed property backed by a Keychain wrapper. Leaving the architecture as-is means a developer who tests with a real key will inevitably commit it.

### `changePercent` nil-quote ambiguity

`Stock.changePercent` returns `0.0` when `latestQuote` is `nil`. There are now two distinct "no data" states — nil quote and `previousClose == 0` — both silently returning `0.0`. Watchlist sorting by change percent (US-03) will place all unloaded stocks among genuinely flat ones. `displayPrice` already uses `guard let … return "--"`; `changePercent` should match:

```swift
var changePercent: Double? {
    guard let q = latestQuote, q.previousClose > 0 else { return nil }
    return ((q.close - q.previousClose) / q.previousClose) * 100
}
```

This change also motivates making `Quote.previousClose` an optional (`Double?`), so the guard at the `Quote` level is explicit rather than relying on the `> 0` sentinel.

### Direction-blind P&L in Trade

`Trade.unrealizedPnL(currentPrice:)` computes `Double(quantity) * (currentPrice - entryPrice)`. The `TradeDirection` enum's `Codable` raw value is already being written to disk wherever `Trade` is archived. Adding `short` without updating this formula produces wrong P&L silently on every short position:

```swift
func unrealizedPnL(currentPrice: Double) -> Double {
    let multiplier: Double = direction == .long ? 1 : -1
    return multiplier * Double(quantity) * (currentPrice - entryPrice)
}
```

`realizedPnL` has the same direction-blindness and needs the same fix.

### Degenerate risk/reward in TradeSignal

```swift
var riskReward: Double {
    guard stopLoss != entryPrice else { return 0 }
    let risk   = abs(entryPrice - stopLoss)
    let reward = abs(takeProfit - entryPrice)
    return risk > 0 ? reward / risk : 0
}
```

The outer `guard` is unreachable as a second defence because `abs(entryPrice - stopLoss)` will be `0` whenever `stopLoss == entryPrice`, making `risk > 0` false anyway. The deeper problem: returning `0` makes a malformed signal look like a signal with a 0:1 R:R — a bad but valid-looking value. FR-03.4 requires a valid stop-loss on every emitted signal; the engine should enforce this precondition so `riskReward` never receives degenerate input. In the meantime, `riskReward` should return `Double?` (returning `nil` for zero risk) so callers can distinguish "zero R:R" from "invalid signal."

### Codable gaps

`ConfidenceTier` has no `Codable` conformance. As a computed property on `TradeSignal`, this doesn't affect encoding today. The risk is that FR-02.2 requires user-configurable indicator parameters, and a natural extension is user-configurable tier thresholds — at which point `tier` becomes a stored property and the `Codable` synthesis on `TradeSignal` breaks silently at runtime on any archive that predates the change. Conforming it now (`RawRepresentable` with a `String` raw value means synthesis is one word) prevents a future migration.

### Test coverage

`DayTraderTests` is empty. The financial math in these models is exactly the class of logic that should be unit-tested before any UI is built on top of it. Not tested:

- `TradeSignal.riskReward` with `stopLoss == entryPrice` and with `takeProfit == entryPrice`
- `Trade.unrealizedPnL` sign correctness for both directions
- `Stock.changePercent` with `previousClose == 0` and with `latestQuote == nil`
- `ConfidenceTier.init(score:)` at the boundary values `0.60` and `0.80` exactly
- `Quote.typicalPrice` arithmetic and `isGreen` on a doji (`open == close`)
- `Portfolio` daily P&L, win rate, and profit factor once that type exists
